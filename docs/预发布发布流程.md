# 部署与预发布教程

本文区分本地双节点演练、Windows 本机 Node Agent 和 GitHub 预发布构建。当前仓库提供可重复的测试部署和预览构建；Linux/NAS 容器镜像用于 CI 资源模拟，尚不构成可直接暴露网络的生产部署方案。

## 1. 选择部署方式

| 目标 | 当前支持方式 | 重要边界 |
| --- | --- | --- |
| 验证同步、故障恢复和 ACL | Docker Compose 双节点模拟 | 仅虚构数据；Docker named volume；API 端口只映射到本机 |
| 下载预构建 Node Agent | GitHub Pre-release 的 Linux x86_64 Docker 镜像归档 | 可用 `docker load` 导入运行；依赖 Linux Secret Service 才能启用节点身份配对；未验收 ARM64/NAS 生产环境 |
| Windows/Linux x64 Node Agent | GitHub Pre-release 的 ZIP/TAR.GZ 软件包，内含 Node.js runtime | 下载并校验软件包后手动解压，运行包内启动器；Linux 配对仍需 Secret Service；暂无 ARM64 包 |
| Windows 源码运行 | 原生 Node.js 开发/测试 | 面向贡献者；API 默认只监听 `127.0.0.1`；Windows Credential Manager 保存身份密钥 |
| Windows 桌面预览 | GitHub prerelease 中的 Tauri NSIS 安装包 | 当前为未签名构建，Windows 可能显示未知发布者/SmartScreen 警告；下载后先核验 SHA-256，仅在测试设备安装 |
| Android 预览 | GitHub prerelease APK | CI 每次运行使用临时签名密钥；更新候选可能需要卸载旧版 |
| Linux/NAS 长期运行 | 尚未作为生产部署支持 | Linux 密钥存储需要 Secret Service；普通 headless 容器通常没有该服务。CI 的 2 GiB x86_64 镜像模拟不能代替 NAS 安装或 ARM64 验收 |
目前不要将 Node Agent 的 HTTP API 直接发布到公网或不可信 LAN。API 需要可信的本机边界；节点 P2P 身份认证不能替代 API 的 TLS、账户管理和网关安全。NAS 正式部署教程应等容器密钥存储、网络入口和备份恢复方案通过验收后再发布。

## 2. Docker Compose 双节点演练

### 先决条件

- Windows 10/11、WSL2 或 Linux 主机，已启动 Docker Desktop/Engine。
- Docker Compose v2、Node.js 22.12 或更高版本、pnpm 11。
- 仓库依赖已安装；使用本地虚构数据，不要挂载个人照片目录。

### 启动和运行验收

从仓库根目录执行：

```powershell
pnpm install --frozen-lockfile
docker compose -f deploy/compose/docker-compose.sync.yml up -d --build
docker compose -f deploy/compose/docker-compose.sync.yml ps
pnpm test:sync-compose
```

Compose 启动 `windows-sim` 与 `nas-sim` 两个独立 Node Agent。它们各自使用 SQLite、身份 fixture 和原图 volume，只通过一个私有 bridge 网络通信。宿主机 API 端口只绑定到 loopback：`127.0.0.1:18443` 和 `127.0.0.1:18444`。测试管理员令牌固定写在 Compose fixture 中，绝不能复制到真实部署。

查看服务状态和日志：

```powershell
docker compose -f deploy/compose/docker-compose.sync.yml ps
docker compose -f deploy/compose/docker-compose.sync.yml logs --tail 100 windows-sim nas-sim
Invoke-RestMethod http://127.0.0.1:18443/v1/health
Invoke-RestMethod http://127.0.0.1:18444/v1/health
```

健康检查成功后，集成脚本会配对两个节点、分别上传不同的合成原图、验证授权索引访问、断开并恢复 NAS 节点、重启节点并检查事件最终收敛。重复运行会复用专用 named volumes，脚本不会自动删除它们。

停止容器并保留测试数据：

```powershell
docker compose -f deploy/compose/docker-compose.sync.yml down
```

只有确认该 Compose 工程仍是一次性模拟数据时，才重置其专用 volume：

```powershell
docker compose -f deploy/compose/docker-compose.sync.yml down -v
```

`down -v` 会永久删除两个模拟节点的数据库、fixture 身份和模拟原图。不要对包含真实图库或用户 bind mount 的 Compose 工程执行此命令。容器运行在 Linux 内核上，不能证明真实 Windows/NTFS 行为。

## 3. Windows 本机启动 Node Agent

### 从下载到第一次启动：Windows 节点

本节给第一次安装者一条完整路径。当前受支持的是 Windows 本机预览/测试；NAS/生产容器部署尚未验收。先在没有重要照片的电脑和空图库目录里操作。

1. 在 [PhotoMesh GitHub 页面](https://github.com/LingBrian/PhotoMesh) 下载 **Code → Download ZIP** 并解压；或先安装 [Git for Windows](https://git-scm.com/download/win)，运行 `git clone https://github.com/LingBrian/PhotoMesh.git D:\PhotoMesh\PhotoMesh`。此步骤下载的是源码。
2. 安装 [Node.js 22.12+](https://nodejs.org/en/download) 和 Git。重新打开 PowerShell，运行 `node --version`、`git --version` 确认安装成功。
3. 在 PowerShell 启用 pnpm：`corepack enable`，再运行 `corepack prepare pnpm@11.25.0 --activate`。检查 `pnpm --version`；若根 `package.json` 的 `packageManager` 指定了不同版本，以仓库指定版本为准。
4. 创建数据目录和空的示例照片目录，设置当前 PowerShell 会话的环境变量：

```powershell
New-Item -ItemType Directory -Force D:\PhotoMesh\agent-data | Out-Null
New-Item -ItemType Directory -Force D:\PhotoMesh\sample-photos | Out-Null
$env:PHOTOMESH_DATA_DIR = 'D:\PhotoMesh\agent-data'
$env:PHOTOMESH_EXTERNAL_ROOTS = '[{"rootId":"demo-photos","libraryId":"demo","path":"D:\\PhotoMesh\\sample-photos","pathStyle":"win32"}]'
$env:PHOTOMESH_ADMIN_TOKEN = [Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
```

5. 进入解压/克隆后的仓库目录，安装依赖并编译 Node Agent：

```powershell
Set-Location D:\PhotoMesh\PhotoMesh
pnpm install --frozen-lockfile
pnpm --filter @photomesh/node-agent build
```

6. 在这个窗口启动 Agent 并保持窗口打开：`pnpm --filter @photomesh/node-agent start`。数据库和托管上传内容写入 `agent-data`；服务默认仅监听本机 `127.0.0.1:8443`。
7. 另开 PowerShell 运行 `Invoke-RestMethod http://127.0.0.1:8443/v1/health`。得到健康响应后才继续；向 `sample-photos` 放入少量测试照片，确认它们只被索引而没有被更改。按 `Ctrl+C` 正常停止。

每个新 PowerShell 会话都需要重新设置三个 `$env:` 变量，或使用仅当前 Windows 用户可读的本机环境配置。不要把管理员令牌写入仓库、截图或公开日志。外部目录扫描只读；数据目录必须与原图目录分开。

### 准备数据位置

安装 Node.js 22.12+ 和 pnpm 11。建议把 PhotoMesh 数据目录与原图目录分开：数据目录包含 SQLite、托管上传原图和运行状态；外部来源目录将以只读方式扫描。先在空的测试目录演练：

```powershell
New-Item -ItemType Directory -Force D:\PhotoMesh\agent-data | Out-Null
New-Item -ItemType Directory -Force D:\PhotoMesh\sample-photos | Out-Null
$env:PHOTOMESH_DATA_DIR = 'D:\PhotoMesh\agent-data'
$env:PHOTOMESH_EXTERNAL_ROOTS = '[{"rootId":"demo-photos","libraryId":"demo","path":"D:\\PhotoMesh\\sample-photos","pathStyle":"win32"}]'
```

根目录清单必须由图库所有者明确选择。扫描器不会修改外部原图；不要把整个磁盘或系统目录加入白名单。

### 启动服务

```powershell
pnpm install --frozen-lockfile
pnpm --filter @photomesh/node-agent build
pnpm --filter @photomesh/node-agent start
```

首次运行时，Agent 在 `PHOTOMESH_DATA_DIR` 下创建 SQLite 数据库并执行迁移；迁移钩子会在迁移前生成数据库备份。服务默认只监听 `127.0.0.1:8443`。另开一个 PowerShell 检查：

```powershell
Invoke-RestMethod http://127.0.0.1:8443/v1/health
```

关闭 PowerShell 前按 `Ctrl+C`，等待进程退出后再复制数据库或升级程序。备份时应同时保留数据目录和原始外部文件所在的独立备份；索引数据库不包含外部来源的原始文件内容。身份私钥由当前 Windows 用户的 Credential Manager 管理，因此应以同一 Windows 用户运行后续进程；不要尝试从日志或仓库导出私钥。

### 配对与网络

局域网 P2P 配对仅在 Agent 绑定到明确的私有网卡地址时启用。先确认网卡地址是静态/可预测的私有地址，再在启动 Agent 的同一 PowerShell 会话设置，例如：

```powershell
$env:PHOTOMESH_LAN_BIND_ADDRESSES = '192.168.1.20'
$env:PHOTOMESH_P2P_PORT = '4001'
```

重启 Agent 后，LAN pairing listener 使用已配置地址和端口。若网络防火墙需要规则，只允许可信家庭/实验室子网访问 P2P 监听端口；不要开放 Node Agent HTTP API 端口给局域网或公网。另一节点应通过短期邀请二维码或手动 IP 发起双向身份验证，核对对端身份后再批准，并只授予所需图库读取权限。撤销设备后，确认其索引访问被拒绝。

不要设置 `PHOTOMESH_FIXTURE_MODE` 或使用 Compose 中的固定管理员令牌启动真实 Agent；该模式只服务隔离测试。`PHOTOMESH_ADMIN_TOKEN` 也不是公网认证方案。

## 4. 下载预发布软件包

在 [GitHub Releases](https://github.com/LingBrian/PhotoMesh/releases) 选择标记为 **Pre-release** 的版本：

1. 阅读该版本的 Changelog、验收报告摘要和平台限制。
2. 下载对应平台资产及 `SHA256SUMS.txt`，本地执行 SHA-256 校验后再安装。
3. 当前 Windows NSIS 安装包未签名，系统可能提示未知发布者或 SmartScreen 警告；先验证 SHA-256，仅在你主动选择的测试设备上继续。
4. Android APK 的签名密钥不会跨构建保留。安装另一轮临时签名候选前，先备份测试数据，再卸载旧候选。
5. 使用虚构图库完成节点配对、权限撤销、上传完整性和重启恢复演练。不要把预发布版作为唯一原图副本。

Release 页面不存在目标版本时，表示该候选未发布或 CI 尚未通过；不要从 Actions 的中间 artifact 推断预发布已完成。

## 5. 维护者：运行 prerelease 工作流

### 合入准备

所有源代码和文档先通过 PR 合入 `main`。常规 PR `required-ci` 包含 lint、typecheck、Vitest 覆盖率、Flutter test、OpenAPI/JSON Schema 检查、构建和 Tauri 原生检查；耗时的 10 万条 Playwright 验收由预发布门禁运行。先检查 PR 中全部必需任务成功，再合并。

### 触发候选构建

在 GitHub Actions 打开 **Build and publish prerelease**，选择 `main`，输入 `0.x.y-alpha.n`、`0.x.y-beta.n` 或 `0.x.y-rc.n`。也可以从已登录的 GitHub CLI 触发：

```powershell
gh auth status
gh workflow run prerelease.yml --ref main -f version=0.1.0-rc.2
gh run list --workflow prerelease.yml --limit 5
```

使用尚未发布的版本号。追踪本次 run，等 `Release acceptance gate`、Web/NAS、Android、Windows 和最终 publish job 全部结束：

```powershell
gh run watch <RUN_ID> --exit-status
gh run view <RUN_ID> --json status,conclusion,jobs,url
```

门禁会生成机器可读验收报告、失败定位、Changelog、SBOM 和候选归档；平台构建生成 Web、Linux x86_64 NAS 镜像、Windows/Linux x64 Node Agent 包、Android APK 和未签名的 Windows NSIS 安装包。Release 页面只列出这些软件包，以及仓库发布规则要求的 Changelog、SBOM 和 SHA-256 清单。安装脚本、候选文件清单和验收/性能报告保留在源代码或 Actions artifact，不作为 Release 附件。通过后，CI 生成构建来源证明并创建 GitHub prerelease。验收或任一平台构建失败时，publish job 应跳过；修复后合入 main，再用新的候选版本重新触发。

### 发布后核对

确认 Actions run 的结论为 `success`，然后查看 release 的 prerelease 标志和资产：

```powershell
gh release view 0.1.0-rc.2 --json url,isPrerelease,tagName,assets
```

检查平台软件包、Changelog、SBOM 和 SHA-256 清单齐全；验收证据和性能报告应从对应 Actions artifact 获取，不作为 Release 附件。Windows 安装包为未签名版本，会显示未知发布者提示。下载后在本地校验：

```powershell
Get-FileHash .\PhotoMesh-0.1.0-rc.2-windows-x64-unsigned.exe -Algorithm SHA256
```

将结果与 Release 中对应的 SHA-256 清单逐项比对。发布后在一台无重要照片的干净设备上做安装/卸载和升级验证。Stable 需要单独人工验收、商业签名密钥和明确审批；本工作流只接受 alpha、beta 和 rc 版本，不能发布 Stable。

## 6. 验收报告的适用范围

CI 的 100k 文件/事件使用合成元数据，合成内容不等同于真实照片/视频的吞吐基准。当前 NAS 资源检查是在 x86_64 容器上限为 2 GiB 内存，不是 ARM64 仿真或真实 NAS 验收。报告必须保留这些边界；未通过要求或报告 `blocked` 时，不得把产物标记为可发布候选。
